## 一、结论先行

- V38 设计目标达成：**一次采购按 sku×qty 下单 → 发货前厂家逐台登记（序列号+二维码+车架号+电机号+主要元件编号）→ 每台登记生成一台可流转资产（1 SKU → N 资产）**，并融合产品端/商品端核心事件。
- **独立验证通过**：真实 PostgreSQL 干净应用 V38、4 个目标测试类 17/17 绿、全量 150 用例修复后 0 失败、前端 `npm run build` 0 错、ArchUnit 跨域边界生效。
- **验证中逮到 1 个真实回归（已修复）**：电池（BATTERY）资产 `owner_id` 被写成操作人而非买家，且 `createBattery` 本就未建立产权。违反"资产诞生即归属买家"。

## 四、真实回归与修复

**🔴 回归**：`ProvisionOwnershipAuditTest.battery_provision_must_set_buyer_owner_and_grant_ownership` 失败 —— 期望买家(5) 实得操作人(99)。
**根因**：`CreateBattery` record 无 `ownerId` 字段；`createBattery` 把 `operatorId` 当 owner；`provisionFromRegistration` BATTERY 分支未传买家 `ownerId`；且 `createBattery` 本就**未调 `grantOwnership`**（兄弟方法 `createVehicle`/`createDrone` 都调）——导致电池资产即便归属正确也缺 OWNER 角色 + MANAGE ACL。

**修复**（工程师寇豆码，已复测全绿）：
- `AssetRequests.java`：`CreateBattery` 增 `Long ownerId` 字段（与 `CreateVehicle`/`CreateDrone` 对齐）。
- `AssetService.java:96-97`：`createBattery` 改为 `ownerId = req.ownerId()!=null?req.ownerId():operatorId`，构造资产用 `ownerId`。
- `AssetService.java:109`：`createBattery` 补 `grantOwnership(ownerId, asset.getId())`（幂等，ACL 已存在则跳过）。
- `AssetService.java:328`：`provisionFromRegistration` BATTERY 分支将买家 `ownerId` 传入 `CreateBattery`。

修复后：`ProvisionOwnershipAuditTest` 2/2 通过；三分支（VEHICLE:316 / DRONE:322 / BATTERY:328）一致传 `ownerId`；全量 `mvn -o clean test` 150/150 全绿。

## 五、待周老板决策的 2 个覆盖缺口（非 bug）

1. **`assetNo` 自动化断言缺失**：`OrderRegistrationTest` 把 `provisionFromRegistration` 整个 mock 掉，未断言生成 `assetNo` 非空且唯一。当前靠源码兜底（`generateAssetNo()` 返回 `"ASSET-"+UUID`）。建议补一条走真实 `AssetService` 的断言。
2. **"按电机号/电池号反查资产"后端缺端点**：`replaceComponent` 需调用方先持 `assetId`；`AssetController` 仅有列表/`{id}`/`{id}/lifecycle` 三个读端点，无按 `component_nos_json` 反查。若产品预期"输入电机/电池号即定位资产"，需补搜索端点；否则由前端从资产列表过滤（需明确前端职责）。
