# 爪平台 · 增量设计：资金路由与清分（Fund Routing & Clearing）v1

> 配套文档：《账号资金与结算体系设计方案 v1》《资金路由与清分方案 v1》。
> 本文是**落地设计**：在既有 `LedgerService` 之上，补齐 **L2 托管资金层** 与 **L5 统一分账/清分层**，
> 打通 **R1 扫码购分账** 与 **R5 共享池分成** 两个首发场景。
> 目标读者：后端工程师、财务、合作通道方。
> 交付形态：**纯设计，不改代码 / 不建迁移**。所有 DDL 为草案，落地由工程按 §2 执行。

## 0. 结论先行（TL;DR）

| 项 | 结论 |
|---|---|
| 复用 | **完全复用** `LedgerService.postEntries / createAccount / getPlatformAccountId / getBalance / entriesOfTxn`、`AccountService`、`PaymentService`、`PaymentGatewayFactory`、`ReconciliationService/Run`。**不重造复式记账。** |
| 新增 | L2：`funds_location`（账户映射）+ `virtual_subaccount`（虚拟子户）；L5：`settlement_rule`（分账规则）+ `clearing_instruction`（清分指令）+ `settlement_batch(+item)`（结算批次）+ `suspense_entry`（差错挂账）。 |
| 迁移 | **V128–V131** 四个迁移（详见 §2）。**绝不修改 V1–V127。** |
| 首发 | R1（扫码购分账）、R5（共享池分成）**两个都做**，均以 **「分账 at source」为首选**，`到账即清 / 周期批量(T+N)` 为回退。 |
| 铁律 | 平台**只下指令、不划资金**；客户资金与公司自有资金**物理/科目双隔离**；分账 `at source` 时账本零存量。 |
| 关键风险 | ① **购销开票 vs 货款直结** 的税务一致性（§6，**必须税务顾问定案**）；② **ABA/Bakong 是否原生支持分账（split）未确认**——凡涉及真实分账 API 处**一律标注「待通道确认」，严禁臆造接口**（§7）。 |
| 硬约束提醒 | `accounts.balance` 现有 CHECK `balance >= 0 OR account_type='MASTER'`（V37）。新增科目若需负余额，**必须用 MASTER(user_id=NULL) 或在新迁移中放宽该 CHECK**（详见 §1.3、§2.1）。 |

## 1. 实现方案（架构分层 + 与 LedgerService 的精确对接点）

### 1.1 架构分层（在现有代码上的落位）

```
L6 制度层   结算周期(T+7 货款) · KYC 分级 · 限额 · 差错处理 · 报备留痕（本期预留字段，不接真实牌照）
L5 分账层   ★新增 domain.clearing：SettlementRule → SplitEngine → SettlementBatch → ClearingInstruction → 多方入账
L4 结算层   复用/增强：PaymentService · ReconciliationService · Outbox（异步结算触发）
L3 账本层   ★复用 domain.ledger：LedgerService(复式/幂等/悲观锁/余额校验) · AccountService
L2 托管层   ★新增 domain.funds：FundsLocation(账本↔真实托管账户映射) · VirtualSubAccount(虚拟子户)
L1 通道层   ★复用 domain.payment：AbaGateway(ABA 主) · BakongGatewayProvider(辅) · PaymentGatewayFactory(容灾)
```

**核心思想**：L3 已有且达生产级（借贷平衡 + `bizType+bizRef` 幂等 + `SELECT FOR UPDATE` + 余额校验 + 平台内部户豁免）。
本增量**只补 L2（托管映射）与 L5（分账引擎）**，L1/L4 做增强。

### 1.2 与现有 `LedgerService` 的**精确对接点**

| 现有方法 | 复用方式 | 说明 |
|---|---|---|
| `postEntries(BizType, String bizRef, List<Entry>)` | **直接复用**，是所有资金动作的**唯一出口** | 分账/清分过账一律走它；**不新增旁路写账** |
| `createAccount(AccountType, userId, assetId)` | **复用**（用于建虚拟子户对应的账本账户） | 但仅支持 USD，见下 |
| `getPlatformAccountId()` | **复用**（平台对冲侧 MASTER 户） | 分账「平台侧」借方/贷方的通用对冲户 |
| `getBalance(accountId)` / `entriesOfTxn` / `entriesOfAccount` | **复用**（对账/审计读侧） | L2/L3 对账数据源 |
| `AccountService.getOrCreatePlatformAccount(type)` / `getOrCreateUserAccount(userId)` / `getOrCreateSubAccount(userId,type)` | **复用**（跨域资金唯一出口，ArchUnit 守护） | 分账各方账户经它取/建 |

**需要在 `LedgerService` / `AccountService` 新增的方法（最小必要）**：

```java
// ---- AccountService：多币种支持（现有方法全部硬编码 "USD"）----
Account getOrCreatePlatformAccount(AccountType type, String currency);   // USD/KHR/CNY
Account getOrCreateUserAccount(Long userId, AccountType type, String currency);
Account getOrCreateSubAccount(Long userId, AccountType type, String currency);
Optional<Account> findAccount(Long userId, AccountType type, String currency); // 只读，不建户

// ---- LedgerService：清分/对账所需的只读聚合（不改写账路径）----
/** L2/L3 对账：按科目类型汇总某期间净额（ΣC-ΣD），用于「客户资金合计 == 托管余额」。 */
BigDecimal netByAccountType(AccountType type, String currency, Instant from, Instant to);
/** 按 bizType + 期间拉分录（清分批次勾对用，返回 common 层视图，不泄漏实体）。 */
List<LedgerViews.EntryView> entriesByBizTypeAndPeriod(BizType bizType, Instant from, Instant to);
```

> **设计原则**：`postEntries` 的语义、幂等键、借贷平衡校验**一律不改**。清分只是「**在上层把一笔业务拆成 N 条 `postEntries` 调用**」（用 `bizRef` 后缀区分，如现有 `:RELEASE` / `:COMMISSION` / `:BALANCE` 的成熟写法），
> 从而**零改动**复用整个复式引擎与并发保护。

### 1.3 ★ 关键约束：`accounts.balance >= 0` CHECK（V37）

V37 已加约束：`CHECK (balance >= 0 OR account_type = 'MASTER')`。
`LedgerService.postEntries` 对「`MASTER` 且 `user_id == null`」的平台内部户**豁免**余额充足校验（可透支/可负），其余账户**借记不得超余额**。

**结论**（新增科目必须遵守）：
1. **负债类科目**（应付厂家/站/物流/保险）——贷方累计为正，正常；但**放款时借记须保证已先贷记**（顺序敏感）。
2. **资产/桥接类科目**（备付金在途）——在「收单入账」时借记增加，正常。
3. 任何**需要净负余额**的角色（对冲/桥接），**必须使用 `account_type='MASTER'` 且 `user_id=NULL`**，否则会触发 42251/42261。
4. 若确需让新科目可负，**只能新增迁移**（如 V128 内 `DROP CONSTRAINT` + 以放宽口径重建），**绝不改 V37 文件**。

## 2. 新增迁移清单（V128 起，共 4 个）

> 均为 **ADD-ONLY**（`CREATE TABLE IF NOT EXISTS` / 新增列 / 重建约束），全量幂等，`SET search_path = claw;`，表名**不加 `claw.` 前缀**（与 V87/V126/V127 一致）。
> **6 张业务表合并为 4 个迁移**：L2 两张同属「托管映射」一并落地；`clearing_instruction` 与 `settlement_rule` 同属「分账/清分核心」，同批建并在 V131 播种规则；批次与差错各自成批。

### V128__funds_location_and_virtual_subaccount.sql —— L2 托管资金层

**用途**：显式回答「每笔钱在哪家机构的哪个账户」+「虚拟子户 ↔ 账本账户」映射；**破产隔离**在 `location_type` 上显式建模。

```sql
SET search_path = claw;

-- ① 托管点位（账本账户 ↔ 真实托管/备付金账户）
CREATE TABLE IF NOT EXISTS funds_location (
    id                  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    location_code       VARCHAR(48)  NOT NULL UNIQUE,   -- ABA_PAYWAY_RESERVE / BANK_ESCROW_01 / MPTC_DIRECT
    institution         VARCHAR(64)  NOT NULL,          -- ABA / BAKONG / BANK_X
    institution_acct_no VARCHAR(64),                    -- 脱敏存（建议仅后 4 位 + 指纹）
    location_type       VARCHAR(24)  NOT NULL,          -- PLATFORM_OWN / CLIENT_CUSTODY / MERCHANT_DIRECT
    channel             VARCHAR(32),                    -- ABA_PAYWAY / BAKONG / BANK
    currency            CHAR(3)      NOT NULL DEFAULT 'USD',
    covers_account_types VARCHAR(256),                  -- 覆盖账本科目（逗号分隔，审计用）
    status              VARCHAR(16)  NOT NULL DEFAULT 'ACTIVE',
    last_reconciled_at  TIMESTAMPTZ,
    tenant_id           BIGINT       NOT NULL DEFAULT 1,
    deleted             BOOLEAN      NOT NULL DEFAULT FALSE,
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_fl_type ON funds_location (location_type, currency, status);

-- ② 虚拟子户（用户/商家不占真实银行账户）
CREATE TABLE IF NOT EXISTS virtual_subaccount (
    id                BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    vsa_no            VARCHAR(48) NOT NULL UNIQUE,      -- 平台生成，机构侧映射
    owner_type        VARCHAR(24) NOT NULL,             -- USER/STATION/MANUFACTURER/INVESTOR/INSURER/LOGISTICS
    owner_id          BIGINT      NOT NULL,
    owner_user_id     BIGINT      REFERENCES users (id),-- 映射到的账本用户（平台内部方为 NULL）
    funds_location_id BIGINT      NOT NULL REFERENCES funds_location (id),
    currency          CHAR(3)     NOT NULL DEFAULT 'USD',
    external_sub_no   VARCHAR(64),                      -- 机构侧子户号 —— 待通道确认是否存在
    status            VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',  -- ACTIVE/FROZEN/CLOSED
    -- 预留（自持牌照规划，本期只留痕不启用）：
    kyc_level         VARCHAR(16),                      -- NONE/BASIC/ENHANCED
    daily_limit       NUMERIC(16,2),                    -- 日限额
    tenant_id         BIGINT      NOT NULL DEFAULT 1,
    deleted           BOOLEAN     NOT NULL DEFAULT FALSE,
    created_at/updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_vsa_owner
    ON virtual_subaccount (owner_type, owner_id, currency, funds_location_id)
    WHERE deleted = FALSE;
CREATE INDEX IF NOT EXISTS idx_vsa_owner ON virtual_subaccount (owner_type, owner_id);
```

> *(草稿中 `created_at/updated_at ... ` 为简写，落地时按 V1 通用规范各写一行 NOT NULL DEFAULT now()。)*

### V129__settlement_rule_and_clearing_instruction.sql —— L5 分账规则 + 清分指令

**用途**：规则表（场景/收款方/基准/优先级/生效期/结算周期）驱动分账；指令单承载每一笔清分动作与状态机。

```sql
SET search_path = claw;

-- ① 分账规则（统一分账引擎的配置源，替代散落各域的分成逻辑）
CREATE TABLE IF NOT EXISTS settlement_rule (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    biz_scene       VARCHAR(24) NOT NULL,   -- CONSIGNMENT_SCAN/RENTAL_SPLIT/TASK_SETTLE/CAPACITY/DEPOSIT/RECOVERY
    payee_type      VARCHAR(24) NOT NULL,   -- MANUFACTURER/STATION/PLATFORM/INSURANCE/LOGISTICS/OWNER
    basis           VARCHAR(16) NOT NULL,   -- RATE / FIXED / TIER
    rate            NUMERIC(9,6),           -- basis=RATE
    fixed_amount    NUMERIC(16,2),          -- basis=FIXED
    tier_json       TEXT,                   -- basis=TIER（阶梯，jsonb）
    priority        INT         NOT NULL DEFAULT 10,  -- 越小越先扣（平台服务费通常最先）
    currency        CHAR(3)     NOT NULL DEFAULT 'USD',
    settle_cycle    VARCHAR(8)  NOT NULL DEFAULT 'T+0', -- T+0/T+1/T+7
    manufacturer_id BIGINT,                 -- 可选：按厂家细分规则
    effective_from  DATE,
    effective_to    DATE,
    rule_version    INT         NOT NULL DEFAULT 1,
    status          VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
    tenant_id       BIGINT      NOT NULL DEFAULT 1,
    deleted         BOOLEAN     NOT NULL DEFAULT FALSE,
    created_at/updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_sr_scene ON settlement_rule (biz_scene, status, priority);

-- ② 清分指令单（幂等键 = instruction_no / idem_key）
CREATE TABLE IF NOT EXISTS clearing_instruction (
    id               BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    instruction_no   VARCHAR(48) NOT NULL UNIQUE,       -- 幂等键
    idem_key         VARCHAR(64) NOT NULL,              -- 业务幂等键（scene+basis_ref+payee）
    scene            VARCHAR(24) NOT NULL,              -- R1..R12
    mode             VARCHAR(16) NOT NULL,              -- AT_SOURCE/ON_ARRIVAL/BATCH
    payer_vsa_id     BIGINT REFERENCES virtual_subaccount (id),
    payee_vsa_id     BIGINT REFERENCES virtual_subaccount (id),
    payee_account_id BIGINT,                            -- 账本收款账户（ledger.accounts.id）
    amount           NUMERIC(18,4) NOT NULL,
    currency         CHAR(3)      NOT NULL DEFAULT 'USD',
    basis_ref        VARCHAR(64),                       -- 依据单号（订单/结算批次）
    ledger_biz_type  VARCHAR(32),
    ledger_biz_ref   VARCHAR(64),
    channel          VARCHAR(32),                       -- ABA_PAYWAY / BAKONG
    status           VARCHAR(16) NOT NULL DEFAULT 'CREATED', -- 见 §6.1
    institution_ref  VARCHAR(80),                       -- 通道回执号 —— 待通道确认
    retry_count      INT         NOT NULL DEFAULT 0,
    fail_reason      VARCHAR(512),
    sent_at          TIMESTAMPTZ,
    acked_at         TIMESTAMPTZ,
    settled_at       TIMESTAMPTZ,
    tenant_id        BIGINT      NOT NULL DEFAULT 1,
    deleted          BOOLEAN     NOT NULL DEFAULT FALSE,
    created_at/updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (idem_key)
);
CREATE INDEX IF NOT EXISTS idx_ci_status ON clearing_instruction (status, created_at);
CREATE INDEX IF NOT EXISTS idx_ci_basis  ON clearing_instruction (basis_ref);
```

### V130__settlement_batch.sql —— 结算批次（货款 T+7、平台自有分润月结）

**用途**：周期汇总 → 审核 → 下发 → 回执 → 对账闭环；`due_date` 承载 T+N。

```sql
SET search_path = claw;

CREATE TABLE IF NOT EXISTS settlement_batch (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    batch_no     VARCHAR(48) NOT NULL UNIQUE,
    biz_scene    VARCHAR(24) NOT NULL,
    cycle        VARCHAR(8)  NOT NULL,          -- T+1 / T+7
    currency     CHAR(3)     NOT NULL DEFAULT 'USD',
    period_start TIMESTAMPTZ NOT NULL,
    period_end   TIMESTAMPTZ NOT NULL,
    due_date     DATE,                          -- 应付日 = period_end + N（货款类 T+7）
    total_amount NUMERIC(18,4) NOT NULL DEFAULT 0,
    item_count   INT           NOT NULL DEFAULT 0,
    status       VARCHAR(16)   NOT NULL DEFAULT 'COLLECTING', -- 见 §6.2
    approved_by  BIGINT, approved_at TIMESTAMPTZ,
    submitted_at TIMESTAMPTZ, settled_at TIMESTAMPTZ,
    fail_reason  VARCHAR(512),
    tenant_id    BIGINT NOT NULL DEFAULT 1,
    deleted      BOOLEAN NOT NULL DEFAULT FALSE,
    created_at/updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_sb_status ON settlement_batch (status, due_date);

CREATE TABLE IF NOT EXISTS settlement_batch_item (
    id                      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    batch_id                BIGINT NOT NULL REFERENCES settlement_batch (id) ON DELETE CASCADE,
    clearing_instruction_id BIGINT REFERENCES clearing_instruction (id),
    payee_vsa_id            BIGINT REFERENCES virtual_subaccount (id),
    payee_account_id        BIGINT,
    amount                  NUMERIC(18,4) NOT NULL,
    currency                CHAR(3) NOT NULL DEFAULT 'USD',
    status                  VARCHAR(16) NOT NULL DEFAULT 'PENDING',
    created_at/updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_sbi_batch ON settlement_batch_item (batch_id);
```

### V131__suspense_entry_and_seed.sql —— 差错挂账 + 种子

**用途**：长款/短款/未匹配/金额不符/汇兑差异的专门科目与工单；播种默认分账规则 + 关键 `system_config`。

```sql
SET search_path = claw;

CREATE TABLE IF NOT EXISTS suspense_entry (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    entry_no     VARCHAR(48) NOT NULL UNIQUE,
    scene        VARCHAR(24),
    diff_type    VARCHAR(24) NOT NULL,   -- CHANNEL_EXTRA/BOOK_EXTRA/AMOUNT_MISMATCH/FX_DIFF/UNMATCHED
    channel_ref  VARCHAR(80),            -- 通道回执/流水号
    ledger_ref   VARCHAR(64),            -- 账本 bizRef
    amount       NUMERIC(18,4) NOT NULL, -- 正=长款, 负=短款
    currency     CHAR(3) NOT NULL DEFAULT 'USD',
    recon_run_id BIGINT,                 -- 关联 reconciliation_runs.id
    status       VARCHAR(16) NOT NULL DEFAULT 'OPEN', -- OPEN/PROCESSING/RESOLVED/WRITTEN_OFF
    resolution   VARCHAR(512),
    resolved_by  BIGINT, resolved_at TIMESTAMPTZ,
    tenant_id    BIGINT NOT NULL DEFAULT 1,
    created_at/updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_se_status ON suspense_entry (status, created_at);

-- 种子：默认分账规则（R1 扫码购：平台服务费优先，其次站佣/物流，余额归厂家）
INSERT INTO settlement_rule (biz_scene, payee_type, basis, rate, priority, settle_cycle, status)
VALUES
  ('CONSIGNMENT_SCAN','PLATFORM',    'RATE', 0.050000,  1, 'T+0', 'ACTIVE'),
  ('CONSIGNMENT_SCAN','STATION',     'RATE', 0.100000, 10, 'T+7', 'ACTIVE'),
  ('CONSIGNMENT_SCAN','LOGISTICS',   'RATE', 0.050000, 20, 'T+7', 'ACTIVE'),
  ('CONSIGNMENT_SCAN','MANUFACTURER','RATE', 1.000000, 99, 'T+7', 'ACTIVE')  -- 残差归厂家（兜底项）
ON CONFLICT DO NOTHING;

-- 种子：制度参数（不硬编码）
INSERT INTO system_config (config_key, config_value) VALUES
  ('SETTLE_CYCLE_GOODS','T+7'),        -- 货款类结算周期
  ('SETTLE_CYCLE_PLATFORM_REVENUE','T+30'),
  ('CLEARING_UNMATCHED_ALERT_HOURS','24')
ON CONFLICT (config_key) DO NOTHING;
```

> ⚠️ 唯一键/幂等：`ON CONFLICT DO NOTHING` 依赖对应唯一约束（`settlement_rule` 若需严格幂等，落地时加 `UNIQUE(biz_scene,payee_type,rule_version)`；`system_config` 已自带 `config_key` 唯一）。

## 5. 程序调用流程（编号时序）

### 5.1 R1 扫码购分账（分账 at source 为主）

```
场景：用户扫码购买寄售商品 $100；货款=厂家+站佣+服务费+物流。
主路径 A（分账 at source，平台零存量）：
 1 客户端 POST /orders（沿用 CustomerOrderService/履约域，不改订单域主流程）
 2 PaymentService.recharge/collect 生成 KHQR（AbaGateway.createKhqr）→ PaymentOrder=PENDING
 3 用户支付成功 → 通道回调 PaymentService.onCallback(orderNo)
 4 onCallback 内调用 ClearingService.settle(basisRef=orderNo, bizScene=CONSIGNMENT_SCAN, total=100)
 5 SplitEngine.compute() 命中 settlement_rule（按 priority：平台5%→站10%→物流5%→厂家残差）
 6 逐腿 postEntries(BizType.CLEARING_SETTLE, orderNo+":PLATFORM|:STATION|:LOGISTICS|:MFG", ...)
     - 借 CUSTODY_BRIDGE(MASTER) 100 / 贷 各子户（厂家/站/物流/平台收入）
     - 借贷守恒；bizRef 后缀保证幂等
 7 ClearingChannelGateway.splitAtSource(orderNo, 100, legs)  ⚠️【待通道确认】
     - 若支持：通道直接拆分到各收款方虚拟子户 → 返回 institutionRef[] → 指令 CREATED→SENT→ACKED→SETTLED
     - 若不支持：走回退路径 B/C
 8 写 clearing_instruction（每条腿一条，mode=AT_SOURCE，status 依 §6.1 推进）
 9 落 RevenueSettlement/FulfillmentSettlement 台账（沿用现有表，审计锚点）
10 日终：ReconciliationService.runDaily → L1通道↔PaymentOrder / L2账本Σ借=Σ贷 / L3托管余额↔客户资金科目合计

回退路径 B（到账即清，准实时 · 适用验收窗）：
 3b 收单到账 → 事件 ON_ARRIVAL → ClearingService.settleOnArrival(basisRef)
 ……后续 5–10 同主路径

回退路径 C（周期批量 T+7，货款/平台自有分润）：
 3c 结算周期到点 → SettlementBatchService.collect(CONSIGNMENT_SCAN,"T+7",from,to) → COLLECTING
 3d approve() → APPROVED → submit() → SENDING → 通道批量代付 → onBatchAck() → SETTLED
```

### 5.2 R5 共享池分成（四方：所有人/站/平台/保险）

```
主路径 A（分账 at source）：
 1 用户发起租赁 → SharedPoolService.completeRental(rentalOrderId, totalFee)（沿用现有）
 2 completeRental 内调用 ClearingService.settle(basisRef=rentalOrderNo, bizScene=RENTAL_SPLIT, total=totalFee)
 3 SplitEngine.compute() 读取 revenue_split_rules（现有 owner/station/platform/insurance 比例）作为规则源之一
    —— 若 settlement_rule 中已为该 scene 配置规则则优先；否则回退现有 RevenueSplitRule
 4 逐腿 postEntries(BizType.CLEARING_SETTLE, rentalOrderNo+":OWNER|:STATION|:PLATFORM|:INSURANCE")
 5 ClearingChannelGateway.splitAtSource(...)  ⚠️【待通道确认】；不支持则回退 B/C
 6 写 clearing_instruction（四方各一条）+ RevenueSettlement（现有台账）
 7 日终三方对账（同 R1 §5.1 步 10）

回退路径 B（到账即清）：收单到账事件触发 settleOnArrival（验收窗后释放）
回退路径 C（周期批量）：SettlementBatchService.collect(RENTAL_SPLIT, cycle,...)（平台自有份额可月结）
```

> **关键**：R1/R5 均**先落 `postEntries`（账本权益实时）**，再驱动通道动作；通道动作失败时**账本不产生净差异**（指令 FAILED/MANUAL，等重试），从而「账实可对」。

## 6. 状态机

### 6.1 `clearing_instruction`
```
CREATED ──send──> SENT ──ack──> ACKED ──settle──> SETTLED
                    │             │
                    └──fail──> FAILED ──retry(≤3)──> RETRY ──> SENT
                                  │
                                  └──exhaust/需人工──> MANUAL ──(admin)──> SENT | SETTLED(幂等同步)
```
- 终态：`SETTLED` / `MANUAL`。
- 幂等：`instruction_no`(UNIQUE) + `idem_key`(UNIQUE) + 账本 `bizType+bizRef` 三重。
- **重发前必须先查回执**，放款类**严禁重复放款**。

### 6.2 `settlement_batch`
```
COLLECTING ──review──> REVIEWING ──approve──> APPROVED ──submit──> SENDING
                                                   │                  │
                                                   │                  ├─全成功──> SETTLED
                                                   │                  ├─部分──> PARTIAL ──> SENDING(补发)
                                                   │                  └─失败──> FAILED ──> MANUAL
                                                   └──reject──> COLLECTING（退回重汇总）
```

## 7. 清分时机实现（通道侧对接点）

| 时机 | 触发点（现有代码位置） | 通道动作 | 平台存量 |
|---|---|---|---|
| **A. 分账 at source** | `PaymentService.onCallback(orderNo)` 成功后 | `ClearingChannelGateway.splitAtSource(...)` ⚠️**待通道确认** | ≈0 |
| **B. 到账即清** | Outbox `ON_ARRIVAL` 事件（新增 handler，仿 `FulfillmentSettlementService`） | `splitAtSource` / 单笔 `payoutToPayee` | 极小 |
| **C. 周期批量 T+N** | 定时任务 `@Scheduled`/运维手工 → `SettlementBatchService.collect` | 批量 `payoutToPayee`（复用 `AbaGateway.payout`） | 周期累计 |
| **D. 阈值触发** | 提现/放款累计 ≥ 阈值 | `payoutToPayee` | 极小 |

**通道对接要素**：
- 调用时机：下单/支付/到账/放款/退款；
- 幂等键：`bizType+bizRef`（沿用现有账本幂等设计）；
- 回调：异步通知 + 主动查询兜底（防丢单）；
- 对账：日对账文件（SSH/SFTP 或 API）；
- 回执：每笔指令必须有 institution 回执号。

> ⚠️ **【待通道确认清单】**（严禁在未确认前臆造 API 签名与字段）：
> 1. ABA PayWay 是否支持**原生分账（split）**、上限比例（国内原生常有 30% 上限）；
> 2. 是否可开**子商户/虚拟子户**承接各收款方、开户要件与周期；
> 3. 批量代付能力、单笔/单日限额、到账时效（T+0/T+1）、费率；
> 4. 对账文件提供方式（API/SFTP）、格式、时效、是否含回执号；
> 5. 回调/主动查询机制；6. 退款时效与费率；7. 争议/拒付责任归属；8. KHQR 到可用余额时点；
> 9. 银行对平台资质要求（牌照/备案/存管协议）。

## 8. 对账与差错（与现有 `ReconciliationService` / `ReconciliationRun` 衔接）

现有 `ReconciliationService.runDaily(date)` 只做「平台账本净额 ↔ ABA 日净额」双边比对，落 `ReconciliationRun`。
本增量**不替换**它，而是在其基础上**扩展为四层**（复用 `ReconciliationRun` 作为批次载体，`detailJson` 承载四层差异）：

| 层级 | 内容 | 新增对接点 |
|---|---|---|
| L1 通道对账 | 通道流水 ↔ `PaymentOrder`/`WalletTxn` | 现有逻辑（保留） |
| L2 账本对账 | 分录 ↔ 各账户余额（`Σ借=Σ贷`） | 新增 `LedgerService.netByAccountType` 校验 |
| L3 托管对账 | 机构托管余额 ↔ 账本「客户资金」科目合计 | **新增**：按 `funds_location` × `netByAccountType` 勾对 |
| L4 全量勾对 | 三方差异 → 分类 → `suspense_entry` | **新增**：`SuspenseService.record(...)` |

**差异分类 → 处理**：

| 类型 | `diff_type` | 处理 |
|---|---|---|
| 通道有、账本无（漏单） | `CHANNEL_EXTRA` | 补录，进 `SUSPENSE` 待确认 |
| 账本有、通道无（假单） | `BOOK_EXTRA` | 挂起，人工核查 |
| 金额不符 | `AMOUNT_MISMATCH` | 差额进 `SUSPENSE`，追因 |
| 汇兑差异 | `FX_DIFF` | 单独科目，月度结转 |

> `suspense_entry.recon_run_id` 关联 `reconciliation_runs.id`，形成「差异 → 工单 → 处置」闭环。

## 12. 专题：「购销开票」与「货款直结厂家」的一致性与税务含义

### 12.1 两种口径的本质冲突
- **购销（merchant of record）**：平台向用户**全额开销项票**；厂家向平台**开进项票**。平台**同时确认收入与成本**。
- **货款直结厂家（分账）**：资金**不落平台**，由通道把货款直接结算给厂家子户。

冲突点：**票据流要求「平台是销售方」，资金流却是「用户→厂家」**，即**三流（合同 / 资金 / 发票）不一致**。

### 12.2 关键澄清：资金「直结」在账本上几乎 = 平台内部划转
客户资金存管主户（ACC-02）是**同一个真实托管账户**，虚拟子户（厂家/站/平台）只是**逻辑归属**。
因此「分账 at source」在**账本上**等价于：`借 客户资金主户 100 / 贷 应付厂家 85、应付站 10、平台收入 5`，再 `借 应付厂家 85 / 贷 客户资金-厂家子户 85`。
→ **资金不落平台 ≠ 票据链断裂**：平台仍可用「应收用户 / 应付厂家」两段在账本上完整承载购销关系。

### 12.3 账务/科目处理建议
- 设「购销桥接」二段科目：
  - **销售段**：`借 应收用户(或客户资金) 100 / 贷 平台销售收入 100`（`BizType.SALES_SETTLE`）。
  - **采购段**：`借 平台采购成本 85 / 贷 应付厂家 85`（`BizType.PURCHASE_SETTLE`）。
  - **结算段**：`借 应付厂家 85 / 贷 客户资金-厂家子户 85`（`BizType.MERCHANT_PAYOUT`）。
- 三专户/服务费：`借 应收用户 5 / 贷 PLATFORM_REVENUE 5`。
- 全程 `Σ借=Σ贷`；「应付类」余额 = 真实待放款金额，可作对账锚点。

### 12.4 VAT 两种方案（需税务顾问定案）
| 方案 | 发票链 | VAT 口径 | 适配度 |
|---|---|---|---|
| **① 全额购销** | 用户←平台销项票（100）；平台←厂家进项票（85） | **全额销项 − 进项抵扣**（平台就差额 15 部分实际纳税） | 与「平台开票给用户」一致；但站佣/物流也需有票，链路长 |
| **② 差额征税（净额/代理）** | 厂家直接向用户开票；平台仅就服务费 5 开票 | 平台**仅就服务费**计税 | 与「货款直结厂家、平台不碰钱」一致；但要求用户与厂家直接构成买卖（居间代理） |

**建议**：
- 若**坚持购销**（平台开票给用户）→ 走**方案①**，全额销项-进项抵扣，并**把站佣/物流也纳入票据链**（否则成本无票、抵扣缺口）。
- 若**坚持货款直结厂家且厂家直开票**→ 走**方案②**，平台按**差额（服务费）**计税，三流天然一致。
- **不可两者混用**：不能「平台全额开销项票」同时「货款直结且平台不确认成本」——会造成**收入虚增 + 成本无票 + VAT 多缴**。
- **三流对齐**：无论哪种方案，账本都必须用「应收用户 / 应付厂家」两段承载，才能与票据流做**三流对账**。

## 附录 B：柬埔寨税务结论与对结算的硬影响（2026-09-13，已核实）

> 来源：GDT/法律原文 + PwC / KPMG / DFDL / VDB Loi / Grant Thornton / Acclime（二手来源冲突处已标注）。**⚠️ 本附录含一处与既有决策的冲突，需周老板重新裁决（见 B.6）。**

### B.1 VAT 基本盘
- 标准税率 **10%**，**抵扣法**（销项 − 进项），**无普适差额征税**；进项抵扣须有合规 Tax Invoice + 供应商 TIN。
- **唯一差额型规则**：对"**经常收购再转售**"或"**代他人销售**"的旧货/代销，应税价值 = **售价与进价之差，或该次销售的佣金**。→ 直接覆盖**寄售/代销**。
- Tax Invoice 法定要件（LoT Art.77）；须于发货/服务/收款后 **7 天内**开出。电子发票 **CamInvoice**（B2G 2025 强制，B2B 目前自愿）。

### B.2 ★ Model A（购销）vs Model B（代理，Prakas 597）
| | **Model A 购销（共享资产租赁适用）** | **Model B 代理（Prakas 597，2018）【寄售已拍板采用】** |
|---|---|---|
| 计税基数 | 平台**全额**销项 − 进项（净额） | **仅佣金**计 VAT 与 1% PTOI |
| 前提 | 无 | 代理人须中/大型纳税人 + 代理合同 + **定价与佣金由委托人定** + **货物交付前所有权属委托人** + **GDT 认可函**（2 年，KHR 400,000） |
| 硬约束 | 若厂家**未登记 VAT** → 进项不可抵，**10% 变真实成本** | **委托人必须是柬埔寨居民纳税人**；境外厂家 → 此路不通，只能退回 Model A |
| 风险 | 毛额基数放大 PTOI/最低税；merchant-of-record 责任 | **未获认可函 → 被重定性为买断，按毛额补 VAT + 罚 10%~40% + 1.5%/月利息** |

> **与既有决策的冲突**：你此前拍板"用户发票由公司开、厂家开给公司"= **Model A**。但按柬税法，**寄售走 Model B 可只就佣金计税**，税负显著更优（条件是厂家为柬居民纳税人且取得 GDT 认可函）。**共享资产租赁**则只有 Model A 适用（Prakas 597 只覆盖"代理销售货物/服务"，不覆盖资产所有权与租金流）。

### B.3 ★★ 预扣税（WHT）——**对结算的硬影响（设计必须新增代扣代缴）**
平台向第三方付款时的**法定扣缴义务**：
| 付款对象/性质 | WHT 税率 | 备注 |
|---|---|---|
| 付**个人**的服务费（管理/咨询等） | **15%** | 付给**已登记纳税人**并取得合规 VAT 发票可豁免（Prakas 578/2024） |
| **动产/不动产租金**（含资产使用权对价） | **10%** | 同上可豁免；**投资人/站点的"资产分成"很可能被定性为租金 → 10%** |
| 付**非居民**（境外母公司/供应商） | **14%** → 中柬协定 **10%** | 需 GDT 事前批准适用协定 |
| 申报缴纳 | 次月 **20 日** | 未扣缴 → 该支出**不得税前扣除** |

> **对结算设计的硬影响**：**平台不是"照分账全额直付"，而要先代扣 WHT 再付净额**。→ 结算链路必须区分 **gross / withheld / net**，并新增 **`WHT_PAYABLE`（应交税费—预扣税）科目**，每笔对外付款生成 WHT 台账与申报数据。**这是当前 T04/T05 设计未覆盖的缺口。**

### B.4 其他
- 平台公司（法人）在柬**自动属中型纳税人**，须月度线上申报 VAT / 1% PTOI。
- **QIP 不豁免 WHT**（投资优惠仅覆盖 TOI/PTOI/最低税等）。
- 跨境：向非居民支付柬来源收入 **14%**（中柬协定 10%）；进口服务**反向征收 10% VAT**（NR-VAT02）。
- 转让定价：Prakas 574（2024）取代 986；关联方=控制权 ≥20%；年度 CIT 须附 **Annex 1**。

### B.5 对工程的增量影响（建议新增 T11）

- **发票链**：平台仅就**自身佣金**向用户开 Tax Invoice；厂家（委托人）向平台（或按 Prakas 597 选项向用户）直接开票，平台凭票抵进项。
- **VAT/PTOI 基数**：仅平台佣金（5% 段）→ 平台实际税负 = 佣金的 10% VAT + 1% PTOI，远低于 Model A 的毛额计。
- **前置合规**：每个寄售厂家入驻时须登记为**柬居民纳税人**且平台须持有其 **GDT 认可函**（2 年期，规费 KHR 400,000，续期 200,000）；认可函缺失 → 该厂家回退 Model A 计税。
- **对结算/账本的影响（已落在 T01–T07）**：`SplitEngine` 仍按 `PLATFORM→PLATFORM_REVENUE(5%) / STATION→PAYABLE_STATION(10%) / LOGISTICS→PAYABLE_LOGISTICS(5%) / MANUFACTURER→PAYABLE_MFG(残差)` 拆分；**Model B 只改变"谁对哪段开票/计税"，不改资金路由与账本借贷守恒**。WHT 见 C.2。
- **GDT 认可函管理**：新增 `manufacturer_tax_profile`（厂家税务档案）记录 `taxpayerRegistered / gdtAgencyApprovalNo / approvalExpiry`，作为 R1 分账前的前置校验维度之一。

### C.2 共享资产租赁（R5）→ Model A + WHT
- **发票链**：平台作为出租人对用户**全额**开 VAT 发票（10%）；付给投资人/站点的"资产分成"被 GDT 高概率定性为**动产租金 → 10% WHT**，付给个人的服务费 → 15% WHT。
- **WHT 代扣引擎（新增 T11，排在 R5/T08 之前）**：结算链路区分 `gross / withheld / net`；新增 `AccountType.WHT_PAYABLE`；每笔对外付款生成 WHT 台账与月度申报底稿。
- **豁免路径**：若收款方为**已登记纳税人且开合规发票** → 适用 Prakas 578(2024) 豁免（本期作为可配置项，默认开启代扣、允许按收款方 `taxpayerStatus` 豁免）。

### C.4 待税务顾问最终裁定（不阻塞工程，按"可配置"实现）
1. 投资人/站点分成的最终定性（租金 10% / 服务费 15% / 利润分配 0%）→ 决定 `whtCategory` 默认值。

6. VAT 登记门槛、滞报罚则口径冲突（二手来源不一致）。
